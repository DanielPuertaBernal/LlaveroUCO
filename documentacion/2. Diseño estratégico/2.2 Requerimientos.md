# 2.2 Requerimientos

Requerimientos del sistema Llavero, verificados contra el código de `LlaveroBack` y `LlaveroFront`. Cada requerimiento indica el módulo que lo implementa.

**Nomenclatura:** `RF-XX` requerimiento funcional · `RNF-XX` requerimiento no funcional · `RN-XX` regla de negocio.

---

## Actores del sistema

| Actor | Tipo | Autenticación |
|---|---|---|
| **Administrador** (`admin_programacion`) | Usuario del sistema | Office 365 o credenciales locales |
| **Auxiliar** (`auxiliar_programacion`) | Usuario del sistema | Office 365 o credenciales locales |
| **Portero** (`porteria`) | Usuario del sistema | Office 365 o credenciales locales |
| **Superadministrador** (`superadmin`) | Usuario del sistema | Bootstrap por variable de entorno |
| **Comunidad** (docente, estudiante, empleado) | Sujeto de negocio | No inicia sesión; se identifica por credencial |
| **ETL institucional** | Sistema externo | API key servidor a servidor |

## Reglas de negocio

| ID | Regla | Dónde se garantiza |
|---|---|---|
| RN-01 | Dos reservas activas no pueden solaparse en el mismo salón, fecha y franja horaria. | Base de datos (`EXCLUDE USING gist`) |
| RN-02 | Un equipo solo puede estar entregado en un préstamo activo a la vez. | Base de datos (índice único parcial) |
| RN-03 | Una persona no puede tener dos llaves del mismo salón el mismo día y horario. | Base de datos (índice único parcial) |
| RN-04 | Una novedad refiere a una llave o a un equipo, nunca a ambos. | Base de datos (`CHECK`) |
| RN-05 | Ningún registro se elimina físicamente; se marca como eliminado. | Base de datos (columna `deleted_at`) |
| RN-06 | No se puede eliminar un registro que aún tenga hijos vivos. | Base de datos (trigger) |
| RN-07 | El estado de una novedad nunca retrocede. | Base de datos + aplicación |
| RN-08 | Un préstamo entra en mora cuando supera el tiempo máximo configurado para el bloque. | Aplicación (`scheduler`) |
| RN-09 | Solo el administrador define la resolución de una novedad; el auxiliar puede cambiar su estado. | Aplicación |
| RN-10 | El portero presta y recibe llaves, pero en equipos solo recibe devoluciones. | Aplicación + frontend |
| RN-11 | El portero no tiene acceso al directorio de comunidad ni a la gestión de monitores. | Aplicación + frontend |
| RN-12 | La ubicación operativa etiqueta la transacción; no filtra qué registros ve un usuario. | Aplicación |
| RN-13 | Solo se admiten correos de los dominios institucionales autorizados. | Aplicación |
| RN-14 | La instantánea de un equipo dentro de un préstamo no cambia si luego se edita el equipo maestro. | Modelo de datos |

## Requerimientos no funcionales

### Seguridad

| ID | Requerimiento | Implementación verificada |
|---|---|---|
| RNF-01 | Las contraseñas locales deben almacenarse cifradas con un algoritmo de hashing adaptativo. | `bcryptjs` |
| RNF-02 | Las contraseñas deben exigir mínimo 8 caracteres, mayúscula, minúscula, número y carácter especial. | `passwordSchema` (Zod) |
| RNF-03 | El token de acceso debe expirar en 8 horas y el de refresco en 7 días, ambos configurables. | `auth.service` |
| RNF-04 | Los tokens de refresco deben almacenarse como hash, nunca en claro. | `usuario_sesiones.token_hash` |
| RNF-05 | El inicio de sesión debe limitarse a 10 intentos por ventana de 15 minutos. | `authLimiter` |
| RNF-06 | La renovación de token debe limitarse a 20 intentos por ventana de 15 minutos. | `refreshLimiter` |
| RNF-07 | Los endpoints de sincronización deben limitarse a 300 llamadas por ventana de 15 minutos, configurable. | `syncLimiter` |
| RNF-08 | La API debe aplicar cabeceras de seguridad HTTP estándar. | `helmet` |
| RNF-09 | El acceso desde el navegador debe restringirse al origen del frontend configurado. | CORS con `CLIENT_URL` |
| RNF-10 | Toda entrada de la API debe validarse contra un esquema antes de llegar a la lógica de negocio. | `zod` + `validate.middleware` |
| RNF-11 | La integración con el ETL debe autenticarse por clave de API, sin sesión de usuario. | `apiKey.middleware` |

### Integridad de datos

| ID | Requerimiento | Implementación verificada |
|---|---|---|
| RNF-12 | Ninguna llave foránea debe borrar en cascada. | `ON DELETE RESTRICT` en todo el esquema |
| RNF-13 | Todo identificador debe ser un UUID v7, generado por la aplicación. | `uuidv7` |
| RNF-14 | Las operaciones de cabecera y línea deben ejecutarse en una sola transacción. | Transacciones Knex |
| RNF-15 | Los índices únicos deben ignorar los registros eliminados lógicamente. | Índices únicos parciales |
| RNF-16 | La marca de última modificación debe mantenerse automáticamente. | Trigger `set_updated_at` |

### Rendimiento

| ID | Requerimiento | Implementación verificada |
|---|---|---|
| RNF-17 | La búsqueda por nombre en el directorio debe usar un índice especializado, no recorrido completo. | Índice GIN con trigramas |
| RNF-18 | Las consultas por estado, fecha y relaciones frecuentes deben estar indexadas. | Índices por columna de filtro |
| RNF-19 | La lectura de programaciones debe evitar reconstruir la unión de subtipos en cada consulta. | Vista `v_programaciones` |
| RNF-20 | Los listados extensos deben paginarse. | `pagination.helper` |
| RNF-21 | La sincronización masiva debe procesarse por lotes. | Repositorio de comunidad |

### Operación y mantenibilidad

| ID | Requerimiento | Implementación verificada |
|---|---|---|
| RNF-22 | El esquema debe evolucionar mediante migraciones versionadas y reversibles. | 21 migraciones Knex |
| RNF-23 | El entorno de desarrollo debe levantarse con un solo comando. | `docker-compose` |
| RNF-24 | Toda la configuración debe leerse de un único archivo de entorno en la raíz. | `shared/config/env.js` |
| RNF-25 | El sistema debe registrar en bitácora cada petición y cada error. | `request.logger`, `error.handler` |
| RNF-26 | El proceso automático de fondo debe ejecutarse cada 5 minutos. | `node-cron` |
| RNF-27 | El sistema debe operar en la zona horaria `America/Bogota` para los cálculos de mora. | `date.helper` |
| RNF-28 | La API debe exponer un endpoint de verificación de estado. | `GET /health` |
| RNF-29 | El código debe organizarse por funcionalidad, no por capa técnica. | `src/features/*` |

### Usabilidad

| ID | Requerimiento |
|---|---|
| RNF-30 | La interfaz debe ser accesible desde un navegador, sin instalación en el equipo del usuario. |
| RNF-31 | La lectura de credencial debe funcionar con lectores RFID de tipo teclado emulado, sin controlador adicional. |
| RNF-32 | Cada rol debe ver únicamente las opciones de menú que le corresponden. |
| RNF-33 | Las operaciones frecuentes de portería deben completarse con el mínimo de interacciones. |

## Restricciones

| Restricción | Detalle |
|---|---|
| **Plataforma** | Aplicación web. No hay cliente de escritorio ni móvil nativo. |
| **Base de datos** | PostgreSQL. El sistema depende de extensiones (`unaccent`, `pg_trgm`, `btree_gist`) y de restricciones de exclusión que no son portables a otros motores. |
| **Identidad** | La autenticación institucional depende de Azure AD (Office 365). |
| **Correo** | El envío depende del relé SMTP interno de la universidad. |
| **Origen de datos** | La programación se importa desde Excel; la comunidad se sincroniza desde el ETL institucional. Ninguno de los dos se administra dentro de Llavero. |
| **Hardware** | Lectores RFID USB de tipo teclado emulado, conectados al equipo de cada usuario. El firmware ESP32 de campo fue retirado del proyecto. |
