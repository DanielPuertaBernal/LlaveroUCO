# 4.2 Diagrama de Clases

Estructura de clases del backend. El sistema sigue un **modelo de dominio anémico**: las entidades son estructuras de datos planas y el comportamiento vive en servicios. Por eso este documento describe sobre todo las clases de **servicio** y **repositorio**, no las de dominio.

Convención de todo el backend: cada servicio y cada repositorio se exporta como **una única instancia** (`module.exports = new XService()`), no como clase. Son singletons sin estado propio más allá de sus dependencias.

---

## Patrón estructural por funcionalidad

Toda funcionalidad repite las mismas cuatro clases y la misma dirección de dependencia.

```mermaid
classDiagram
    direction LR

    class XRoutes {
        <<módulo>>
        +router: Router
        +registrarEndpoints()
    }

    class XController {
        <<singleton>>
        +listar(req, res)
        +obtener(req, res)
        +crear(req, res)
        +actualizar(req, res)
        +eliminar(req, res)
    }

    class XService {
        <<singleton>>
        +listar(filtros)
        +obtener(id)
        +crear(datos)
        +actualizar(id, datos)
        +eliminar(id)
    }

    class XRepository {
        <<singleton>>
        +findAll(filtros)
        +findById(id)
        +create(datos)
        +update(id, datos)
        +deleteById(id)
    }

    class BaseRepository {
        <<clase base>>
        #tableName: string
        +db: Knex
        +table: QueryBuilder
        +findById(id)
        +create(datos)
        +update(id, updates)
        +deleteById(id)
    }

    XRoutes --> XController : delega
    XController --> XService : invoca
    XService --> XRepository : consulta
    XRepository --|> BaseRepository : extiende
```

### Contrato de responsabilidades

| Clase | Conoce | No debe conocer |
|---|---|---|
| `XRoutes` | Express, middleware, controlador | Reglas de negocio |
| `XController` | `req`, `res`, servicio | Knex, SQL, tablas |
| `XService` | Repositorios, otros servicios, transacciones | `req`, `res`, HTTP |
| `XRepository` | Knex, nombres de tabla | Reglas de negocio |

## Infraestructura compartida

```mermaid
classDiagram
    direction TB

    class BaseRepository {
        #tableName: string
        +get db() Knex
        +get table() QueryBuilder
        +findById(id) object
        +findAll(filtros) object[]
        +create(datos) object
        +update(id, updates) object
        +deleteById(id) object
        +existsById(id) boolean
    }

    class PgClient {
        <<singleton>>
        -knex: Knex
        +connect() Promise
        +getKnex() Knex
        +disconnect() Promise
    }

    class ApiError {
        <<Error>>
        +statusCode: number
        +message: string
        +data: object
        +badRequest(msg)$ ApiError
        +unauthorized(msg)$ ApiError
        +forbidden(msg)$ ApiError
        +notFound(msg)$ ApiError
        +conflict(msg, data)$ ApiError
    }

    class Logger {
        -namespace: string
        +info(msg, meta)
        +warn(msg, meta)
        +error(msg, error)
        +debug(msg, meta)
    }

    class EmailService {
        <<singleton>>
        -transporter: Transporter
        +enviar(destinatario, asunto, html) Promise
        +construirDesdeePlantilla(tipo, datos) string
    }

    class EnvConfig {
        <<módulo>>
        +REPO_ROOT: string
        +loadEnv() void
    }

    BaseRepository --> PgClient : obtiene conexión
    EmailService --> Logger : registra
```

| Clase | Responsabilidad |
|---|---|
| `BaseRepository` | Operaciones CRUD comunes. Aplica borrado lógico y genera UUID v7 al crear |
| `PgClient` | Conexión Knex única para todo el proceso |
| `ApiError` | Error tipificado con código HTTP. Construido por métodos estáticos de fábrica |
| `Logger` | Registro con espacio de nombres por módulo |
| `EmailService` | Envío por SMTP con plantillas separadas por tipo |
| `EnvConfig` | Carga del `.env` único, resuelto desde la ruta del módulo y no desde el directorio de trabajo |

> **Detalle de `BaseRepository.update`:** no estampa `updated_at`. Esa columna la mantiene un trigger de base de datos, de modo que ningún camino de escritura pueda olvidarla.

## Autenticación y autorización

```mermaid
classDiagram
    direction TB

    class AuthService {
        <<singleton>>
        +login(usuario, password) TokenPair
        +loginOffice365(codigo, state) TokenPair
        +refresh(refreshToken) TokenPair
        +logout(refreshToken) void
        +revocarSesiones(usuarioId) void
        -generarAccessToken(usuario) string
        -generarRefreshToken(usuario) string
    }

    class AuthOAuth {
        <<módulo>>
        +construirUrlAutorizacion() string
        +intercambiarCodigo(codigo) TokenSet
        +validarState(state) boolean
    }

    class AuthMiddleware {
        <<módulo>>
        +verifyToken(req, res, next)
        +requireRole(...roles) Function
        +requireAdmin: Middleware[]
        +requireAuth: Middleware[]
        +requireAux: Middleware[]
    }

    class AuthConstants {
        <<módulo>>
        +ROLES: object
        +PROVEEDORES_AUTH: object
        +DOMINIOS_AUTORIZADOS: string[]
        +passwordSchema: ZodSchema
        +isDominioAutorizado(email) boolean
    }

    class PorterosService {
        <<singleton>>
        +listar() Portero[]
        +obtener(usuarioId) Portero
        +asignarBloque(usuarioId, bloqueId, permisos)
        +tienePermiso(usuarioId, bloqueId, operacion) boolean
        +tienePermisoGlobal(usuarioId, operacion) boolean
        +eliminar(usuarioId)
    }

    class UsuarioRepository {
        +findById(id)
        +findByUsuario(usuario)
        +findByEmail(email)
    }

    class AuthRepository {
        +crearSesion(usuarioId, tokenHash, expiraEn)
        +buscarSesionPorHash(tokenHash)
        +revocarSesion(sesionId)
    }

    AuthService --> AuthRepository
    AuthService --> UsuarioRepository
    AuthService --> AuthOAuth
    AuthService --> AuthConstants
    AuthMiddleware --> UsuarioRepository
    AuthMiddleware --> AuthConstants
    PorterosService --> UsuarioRepository
```

`requireRole` es una **fábrica de middleware**: recibe los roles admitidos y devuelve el middleware que los comprueba. Eso permite componer atajos legibles en las rutas (`requireAdmin`, `requireAux`) sin repetir la comprobación.

`PorterosService` distingue dos formas de comprobar permisos:

- `tienePermiso(usuarioId, bloqueId, operacion)` — para llaves, que sí están ligadas a un bloque.
- `tienePermisoGlobal(usuarioId, operacion)` — para equipos, que en el modelo de datos actual no pertenecen a ningún bloque. Basta con tener el permiso habilitado en al menos uno.

## Llaves: la funcionalidad con servicio subdividido

`features/llaves` es la única que divide su capa de servicio, por el peso de su lógica.

```mermaid
classDiagram
    direction TB

    class LlaveController {
        <<singleton>>
        +pendientes(req, res)
        +todosPendientes(req, res)
        +historial(req, res)
        +lecturaNFC(req, res)
        +registrarEntrega(req, res)
        +registrarDevolucion(req, res)
        +exportar(req, res)
    }

    class LlaveService {
        <<singleton>>
        +obtenerPendientes(user) Registro[]
        +obtenerTodosPendientes(user) Registro[]
        +obtenerPendientesHoy(user) Registro[]
        +obtenerHistorial(filtros, paginacion) Pagina
        +obtenerClasesProcesadasHoy() Clase[]
        +procesarLecturaNFC(idCarnet, ubicacion, user) Resultado
        +confirmarPrestamoAnticipado(payload, user) Registro
        +registrarEntrega(infoClase, user) Registro
        +registrarDevolucion(documento, ubicacion, user) Registro
        +registrarDevolucionPorId(registroId, ubicacion, user) Registro
        +exportarHistorial(filtros) Buffer
    }

    class LlaveContext {
        <<módulo>>
        +resolverContexto(idCarnet) Contexto
        -buscarPersona(idCarnet) Comunidad
        -buscarProgramacionDelMomento(personaId) Programacion
        -resolverRol(persona, programacion) Rol
        -buscarAutorizacionMonitor(persona, programacion) Monitor
    }

    class LlaveWorkflows {
        <<módulo>>
        +flujoEntrega(contexto, user) Registro
        +flujoDevolucion(registro, ubicacion, user) Registro
        +flujoDevolucionAutomatica(registro) Registro
    }

    class LlaveDomain {
        <<módulo puro>>
        +calcularDuracionMinutos(entrega, devolucion) number
        +calcularEstado(registro, config) string
        +calcularRetrasoEntrega(programacion, entrega) number
        +estaEnMora(registro, tiempoMaximo) boolean
        +toClientFormat(registro) object
    }

    class LlaveReadModel {
        <<módulo>>
        +proyectarPendiente(fila) object
        +proyectarHistorial(fila) object
        +aplicarFiltrosDeRol(query, user) QueryBuilder
    }

    class LlaveWriteModel {
        <<módulo>>
        +construirEntrega(contexto, user) object
        +construirDevolucion(registro, ubicacion, user) object
    }

    class LlaveRepository {
        <<singleton>>
        +findPendientes(filtros)
        +findHistorial(filtros, paginacion)
        +findActivoPorPersonaYSalon(personaId, salonId, dia)
        +crearRegistro(datos, trx)
        +registrarDevolucion(id, datos, trx)
    }

    LlaveController --> LlaveService
    LlaveService --> LlaveContext
    LlaveService --> LlaveWorkflows
    LlaveService --> LlaveReadModel
    LlaveWorkflows --> LlaveDomain
    LlaveWorkflows --> LlaveWriteModel
    LlaveWorkflows --> LlaveRepository
    LlaveContext --> LlaveRepository
    LlaveReadModel --> LlaveRepository
    LlaveWriteModel --> LlaveRepository
```

| Módulo | Por qué existe por separado |
|---|---|
| `llave.context.js` | Resolver quién es la persona, qué clase le corresponde en ese momento y si actúa como docente titular o monitor delegado es lógica sustancial e independiente del flujo de entrega |
| `llave.domain.js` | Cálculos puros y sin efectos: duración, mora, retraso, formato de salida. Es la parte trivialmente comprobable |
| `llave.workflows.js` | Secuencias completas de entrega y devolución, incluida la transacción |
| `llave.read-model.js` | Proyecciones de lectura. Aquí vive el filtrado por rol, que acota al portero a lo que él mismo gestionó |
| `llave.write-model.js` | Construye las formas de escritura, separando el "qué se guarda" del "cómo se decide" |

## Préstamos de equipos

```mermaid
classDiagram
    direction TB

    class PrestamoController {
        <<singleton>>
        +listar(req, res)
        +activos(req, res)
        +obtener(req, res)
        +crear(req, res)
        +registrarDevolucion(req, res)
    }

    class PrestamoService {
        <<singleton>>
        +listar() Prestamo[]
        +activos() Prestamo[]
        +porDocente(codigoNfc) Prestamo[]
        +obtener(id) Prestamo
        +crear(datos, user) Prestamo
        +agregarEquipo(prestamoId, equipoId, auxiliar, user)
        +registrarDevolucion(datos, user) Devolucion
        -_ejecutarTransaccionConDedupe(fn)
        -_cargarEquiposDisponibles(ids, trx)
        -_validarDisponibilidad(ids, trx, mapa)
    }

    class PrestamoRepository {
        <<singleton>>
        +findAll()
        +findActivos()
        +findByDocente(codigoNfc)
        +crearConLineas(cabecera, lineas, trx)
        +marcarEquiposDevueltos(ids, trx)
        +actualizarEstadoCabecera(prestamoId, trx)
    }

    class EquipoService {
        <<singleton>>
        +listar(filtros)
        +obtener(id)
        +crear(datos)
        +actualizar(id, datos)
        +eliminar(id)
    }

    PrestamoController --> PrestamoService
    PrestamoService --> PrestamoRepository
    PrestamoService --> EquipoService
```

Los métodos con prefijo `_` son internos del servicio. `_validarDisponibilidad` comprueba en la aplicación lo que el índice único parcial `ux_prestamo_equipos_equipo_activo` garantiza en la base de datos: es una comprobación temprana para dar un mensaje claro, no la garantía en sí.

## Reservas

```mermaid
classDiagram
    direction TB

    class ReservaService {
        <<singleton>>
        +crear(datos) Reserva
        +validar(datos) Resultado
        +listar(filtros, paginacion) Pagina
        +aprobar(id, aprobadoPor, usuarioId) Reserva
        +rechazar(id, aprobadoPor, usuarioId) Reserva
        +cancelar(id) Reserva
        +editar(id, datos) Reserva
        +disponibilidad(salon, fecha) Franja[]
        +disponibilidadSmart(salon, fecha) Franja[]
        +salonesDisponibles(fecha, inicio, fin) Salon[]
        +sincronizarEstadosVencidos() void
        -_buscarConflictos(datos) Conflicto[]
        -_bulkCompletarVencidas(fecha, hora)
        -_registrarDevolucionAutomaticaPorCancelacion(reserva)
    }

    class ReservaRepository {
        <<singleton>>
        +findConflictos(salonId, fecha, inicio, fin)
        +findVencidas(fecha, hora)
        +crear(datos, trx)
        +actualizarEstado(id, estado, trx)
    }

    class ReservasSemestralesService {
        <<singleton>>
        +listarPorSemestre(semestreId)
        +crearGrupo(datos) Programacion[]
        +cancelarGrupo(grupoId, motivo)
        +cancelarIndividual(id, motivo)
    }

    class ProgramacionService {
        <<singleton>>
        +importarExcel(archivo, semestre) Resumen
        +listar(filtros, paginacion)
        +obtenerOcupacion(filtros)
        +exportarExcel(filtros) Buffer
    }

    ReservaService --> ReservaRepository
    ReservaService --> LlaveService : genera préstamo al aprobar
    ReservasSemestralesService --> ProgramacionService
```

`_buscarConflictos` cruza las **tres** fuentes de ocupación: programación académica, reservas individuales y reservas semestrales. Es la implementación del diferenciador de disponibilidad consolidada descrito en la visión.

`sincronizarEstadosVencidos` es el punto de entrada que invoca el proceso de fondo cada 5 minutos.

## Notificaciones y proceso de fondo

```mermaid
classDiagram

    class NotificacionService {
        <<singleton>>
        +procesarVencimientos() void
        +procesarRecordatorios() void
        +reintentarFallidas() void

        +reenviar(id) Notificacion

        -_construirNovedadDemora(registro) Novedad

    class NotificacionRepository {
        <<singleton>>
        +findPendientesDeEnvio()
        +findListasParaReintento(ahora)
        +crearSiNoExiste(datos)
    }

    class ConfiguracionService {
        <<singleton>>
        +obtenerPorBloque(bloqueId) Configuracion
        +obtenerDefaults() Configuracion
        +actualizar(bloqueId, datos)
    }

    class NovedadService {
        <<singleton>>
        +listar(filtros)
        +crear(datos)
        +tomarEnRevision(id, usuario)
        +resolver(id, resolucion, usuario)
    }

    NotificacionScheduler --> NotificacionService
    NotificacionScheduler --> ReservaService : sincroniza vencidas
    NotificacionService --> NotificacionRepository
    NotificacionService --> ConfiguracionService : lee umbrales
    NotificacionService --> EmailService : envía
    NotificacionService --> NovedadService : escala a novedad
```

`crearSiNoExiste` se apoya en el índice único parcial de la tabla: intenta insertar y trata la violación de restricción como "ya existe". Es control de duplicados a nivel de base de datos, no una comprobación previa susceptible de condición de carrera.

`_calcularProximoReintento` implementa el retroceso exponencial sobre `intentos_envio`.

## Middleware como cadena componible

```mermaid
classDiagram
    direction LR

    class Request {
        +headers
        +body
        +user
    }

    class RequestLogger {
        +registrar(req, res, next)
    }

    class VerifyToken {
        +verificar(req, res, next)
    }

    class RequireRole {
        +comprobar(req, res, next)
    }

    class Validate {
        +validarEsquema(req, res, next)
    }

    class RateLimiter {
        +authLimiter
        +refreshLimiter
        +nfcLimiter
        +syncLimiter
    }

    class ApiKeyMiddleware {
        +requireApiKey(nombreVariable) Middleware
    }

    class ErrorHandler {
        +manejar(err, req, res, next)
    }

    Request --> RequestLogger
    RequestLogger --> RateLimiter
    RateLimiter --> VerifyToken
    RateLimiter --> ApiKeyMiddleware
    VerifyToken --> RequireRole
    RequireRole --> Validate
    Validate --> Controller
    Controller --> ErrorHandler : lanza ApiError
```

Dos caminos de autenticación excluyentes:

- **Sesión de usuario** — `verifyToken` seguido de `requireRole`. Es el camino del navegador.
- **Servidor a servidor** — `requireApiKey('COMUNIDAD_SYNC_API_KEY')`. Es el camino del ETL institucional. No hay sesión ni usuario.

## Mapa completo de servicios

| Servicio | Funcionalidad | Colabora con |
|---|---|---|
| `AuthService` | Inicio de sesión, tokens, sesiones | `UsuarioRepository`, `AuthOAuth` |
| `UsuarioService` | Gestión de cuentas | `UsuarioRepository` |
| `PorterosService` | Permisos por bloque y operación | `PorterosRepository` |
| `ComunidadService` | Directorio y sincronización desde el ETL | `ComunidadRepository` |
| `ProgramacionService` | Importación de Excel, consulta, exportación | `ProgramacionRepository`, `ExcelParser` |
| `ReservasSemestralesService` | Reservas recurrentes por grupo | `ProgramacionService` |
| `LlaveService` | Préstamo y devolución de llaves | `LlaveContext`, `LlaveWorkflows`, `LlaveRepository` |
| `MonitorService` | Autorizaciones de docente a estudiante | `MonitorRepository` |
| `PrestamoService` | Préstamo y devolución de equipos | `PrestamoRepository`, `EquipoService` |
| `EquipoService` | Inventario | `EquipoRepository` |
| `ReservaService` | Reservas puntuales y disponibilidad | `ReservaRepository`, `LlaveService` |
| `NovedadService` | Incidentes y su seguimiento | `NovedadRepository` |
| `NotificacionService` | Cola de correo, recordatorios, escalado | `EmailService`, `ConfiguracionService`, `NovedadService` |
| `ConfiguracionService` | Reglas por bloque | `ConfiguracionRepository` |
| `SalonService`, `BloqueService`, `TipoSilleteriaService`, `UbicacionService` | Catálogos | Sus repositorios |
